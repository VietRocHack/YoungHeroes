## Session 3 — real-device testing immediately paid off

User tried the just-shipped Live call on their actual phone within minutes
of Session 2 landing. Two real bugs surfaced that no amount of the
sandboxed-browser verification in Session 2 would have caught:

- **The Live call was completely broken in production.** The WebSocket
  connection failed on `youngheroes.vietrochack.com`. Root cause: Firebase
  Hosting's rewrite proxy does not forward the WebSocket upgrade handshake to
  Cloud Run — confirmed with a direct `wss://` test against both the custom
  domain and `vietrochack-youngheroes.web.app`, both return `404` (Hosting
  strips the upgrade down to a plain HTTP GET, which hits our
  WebSocket-only route and 404s). Session 2's "verified in production" claim
  only ever tested by connecting straight to the Cloud Run URL, bypassing
  Hosting entirely — a real gap in that verification, not just bad luck.
  Fixed by having the frontend connect directly to Cloud Run for the
  WebSocket instead of through Hosting (`frontend/src/lib/api.js`); confirmed
  the direct connection accepts cross-origin requests from the real domain
  (FastAPI's default WebSocket handler doesn't enforce same-origin).
- **`PracticeDecision.jsx` wasn't vertically centered** — a layout
  regression from adding the universal `BackButton` earlier in the day.
  Removing the old "Cancel" button left only 2 flex children under
  `justify-between`, which stretches them to the screen's extreme top/bottom
  instead of grouping them in the middle. Fixed with `justify-center` + a
  gap instead.
- **User asked for a toggle between the classic and Live call flows** —
  reasonable given the above near-miss plus the still-unverified real-audio
  behavior. Restored the classic cascade (`dispatcher.py`, `voice.py`,
  `models/schemas.py`, `/api/tts`, `/api/stt`, `/api/get_call_states` — all
  deleted in Session 2) instead of leaving it gone, and added a toggle on
  `PracticeDecision.jsx` (`frontend/src/lib/callMode.js`, localStorage,
  defaults to classic) that picks between `PracticeCallClassic.jsx` and
  `PracticeCallLive.jsx`. Verified both paths render distinctly correct
  behavior in the browser (Classic shows a manual "Start Call" button and
  stays on the page; Live auto-connects and auto-navigates away on mic
  failure) and that classic `/api/tts`/`/api/get_call_states` still work
  end-to-end after being restored.

## Session 4 — root-causing why Live disconnects right after the greeting (unfinished)

User did exactly the real-device QA Session 3 flagged as outstanding: got
the mic permission prompt, allowed it, heard the "911, what's your
emergency?" greeting, spoke — and the call ended anyway, dropping straight
to the summary page without the dispatcher ever responding. This session
dug into why. **Not fixed yet — stopped mid-investigation to write this up
before running out of usage.**

### What's confirmed, in order of investigation

1. **Ruled out mic permission as the cause.** Asked the user directly: they
   got the prompt, tapped Allow, and spoke before it ended. So audio really
   was being captured — the bug is somewhere in the pipeline after that.

2. **Fixed a real (but secondary) bug**: `Uncaught InvalidStateError: Cannot
   close a closed AudioContext`, seen live on the user's device. Same root
   cause as a bug fixed earlier in `Session 2`/`3` for the *playback*
   AudioContext (`createPcmPlayer().close()`) — turns out `startMicCapture()`'s
   `stop()` had the identical unguarded `audioContext.close()`, and both
   `handleEndCall` and the component-unmount cleanup call `stop()`, so the
   second call threw. Fixed with the same idempotency guard. **Committed and
   pushed** (`b48b423`) — this one's done regardless of the bigger bug below.

3. **Found the backend was running a badly outdated SDK.**
   `backend/requirements.txt` pins `google-genai==1.3.0`; latest on PyPI is
   `2.25.0`. The installed `LiveConnectConfig` was missing entire feature
   areas that exist in the current API (`realtime_input_config`,
   `explicit_vad_signal`, `input_audio_transcription`,
   `session_resumption`, etc. — checked via `model_fields` on both
   versions). **Upgraded google-genai to 2.25.0 in the local venv only —
   `requirements.txt` NOT yet updated, nothing about this shipped.**

4. **Found a real SDK footgun in the old version** (moot now that we're
   upgrading, but worth knowing): passing `types.LiveClientRealtimeInput`
   or a list of `types.Blob` to the old `session.send()` triggers
   Pydantic's `model_dump(mode="json")`, which base64-encodes `bytes`
   fields using the **URL-safe** alphabet (`-`/`_`) — but the SDK's own
   send() logic only re-encodes to **standard** base64 (`+`//`) if it sees
   raw `bytes`, which it never does here since Pydantic already stringified
   it first. Empirically verified with a throwaway encode comparison.
   Bypassing this (passing a raw dict, or the new SDK's dedicated
   `send_realtime_input()`) sidesteps it. This alone did NOT fix the
   symptom, though — see next finding.

5. **Found what looks like the actual root cause**: `session.receive()` is
   an async generator that **exhausts itself after one `turn_complete`**,
   it does not stay open for the life of the session. Confirmed by having a
   receiver task log every message with `sleep(6)` before sending test
   audio: the receiver task printed its "done" summary and returned *during
   the 6-second sleep*, i.e. right after the greeting's `turn_complete` —
   before any test audio was even sent. **Production
   `backend/src/services/live_call.py`'s `_relay_from_model` has exactly
   this shape**: a single `async for message in session.receive():` loop
   with no outer retry. When it exhausts after the greeting, the coroutine
   returns silently, `asyncio.wait(..., FIRST_COMPLETED)` in `run_live_call`
   sees `model_task` finish, treats it as a natural end
   (`is_prank_call` stays at its initial `False`, `natural_end = True`),
   and the whole call wraps up — with no tool call ever having fired. This
   matches the user's reported symptom exactly: greeting plays, then it
   just ends.

6. **Tried the obvious fix and it's not sufficient by itself.** Wrapped
   `session.receive()` in an outer `while` loop in
   `backend/scripts/live_audio_input_test.py` (re-entering it each time the
   inner generator exhausts) so it keeps listening across turns. Confirmed
   this now stays alive past the greeting. But sending real synthesized
   speech (via Gemini TTS, resampled to 16kHz PCM — genuinely non-silent,
   verified sample stats before testing) through `send_realtime_input()`
   while the fixed receiver loop was live *still* produced nothing for 20
   seconds — no `output_transcription`, no `model_turn`, no tool call,
   nothing. So the receive()-exhaustion bug is real and worth fixing
   regardless, but **something else is also wrong with how the actual audio
   content is being sent/recognized**, not yet identified.

## Session 5 — Live call fixed end-to-end

Picked up Session 4's unfinished investigation.

- **The "real audio gets no response" mystery was a test-harness artifact.**
  Session 4's diagnostic streamed speech and then stopped sending audio
  entirely. With automatic VAD the server needs trailing silence to decide
  the speaker has finished, so it just kept waiting. A real mic keeps
  streaming (silence included), so production never had this problem.
  Re-ran with realtime pacing, silence around the speech, and
  `input_audio_transcription` on: the model transcribed the speech
  correctly and replied within about 1s. The `audio/pcm;rate=16000` MIME
  type and default VAD settings are fine as they are.
- **Fixed the real production bug** in `live_call.py`: `_relay_from_model`
  now re-enters `session.receive()` every turn. Before, it went deaf after
  the greeting's `turn_complete` and the call ended right away (exactly the
  symptom the user saw on their phone). It now returns `None` when no
  `end_call` fired, so `naturalEnd` is only true for a real tool-call end.
- **Migrated off the deprecated `session.send()`** to
  `send_client_content()` (the `<START>` kickoff), `send_realtime_input()`
  (mic audio) and `send_tool_response()`.
- **Fixed the goodbye being cut off.** The backend used to stop relaying the
  moment `end_call` fired, and the frontend closed the player and navigated
  away as soon as `ended` arrived, so the "help is on the way, great job"
  line got truncated. Now the backend drains the model's audio until
  `turn_complete` (10s timeout) before sending `ended`, and
  `PracticeCallLive.jsx` stops the mic and waits for the new
  `createPcmPlayer().whenDrained()` before going to the result screen.
- **Verified end-to-end through the real WS endpoint** on a local uvicorn,
  with a Python client that streams 256ms PCM chunks the way the browser's
  ScriptProcessor does. Two scripted child answers (TTS-synthesized)
  produced: greeting, reply, reply plus `end_call`, the full 5.5s goodbye
  (was about 1.6s before the drain fix), then `ended {naturalEnd: true}`.
  Firestore was marked finished.
- **Bumped `google-genai` 1.3.0 → 2.25.0** in `requirements.txt` after
  re-checking the other paths on the new SDK: classic `/api/tts` (dispatcher
  plus TTS) returns real audio/wav, and a one-off `generate_image()` call
  returns a valid, on-style JPEG.
- Browser-side PCM encoding (`liveAudio.js`) reviewed: 16-bit LE, 16kHz, a
  continuous stream, which matches what the backend now handles. Still not
  exercised with a real mic, because the browser pane blocks mic access.
